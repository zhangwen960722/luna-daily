### 规则类型（三态）★ 核心变化

| 值 | 名称 | 触发条件 | 计价单位 |
|:--:|:---|:---|:---|
| 10 | **字段匹配** | 维度条件（AND，**≥1 条必填**） | 按票 / 按KG / 按m³ / 按数量 |

> **原 `20:公式阈值` 类型已废弃**，能力并入 `40:字段&公式`。
> **根因**：「超重超长」的判定天然是「**维度 且 公式**」（如 `尾程=卡派 AND (长+宽)*2+高>300`），原「规则类型三选一」的模型强迫二选一 —— 要么丢维度、要么丢公式，**模型本身错了**。

### 优惠对象与分期（**2026-09-12 修订，覆盖 09-11 的收缩口径**）

| 决策 | 结论 |
|:---|:---|
| **19. 客户特批进一期（三表统一）** | 「客户特批」由 Phase 2 **改为 Phase 1**，且**三张优惠表（运费优惠 / 泡比优惠 / 附加费优惠）口径统一**——`target_type` 一期同时开放 `10:客户特批` 与 `20:客户等级`。**原「三张优惠表一期口径一致收缩为仅客户等级」作废** |
| 客户特批·前置校验 | `target_type=10` → `target_customers`（多选客户，取客商中心-客户管理启用客户）**必填**；`target_type=20` → `target_levels`（多选等级）**必填**。二者是**两个独立命名空间**，同一 ID 值在两边不算冲突 |
| 客户特批·优先级 | **客户特批 > 客户等级，高覆盖低、不叠加**，特批命中即覆盖等级规则 —— **一期即生效**（原「一期无客户特批，等级匹配即终判」作废） |
| 客户特批·唯一性 | 同一父实体 × 同一对象类型 × 同一目标，最多一条生效规则 |
| **20. 审批编号进一期** | `approval_no`（飞书审批编号，字符串30）：**客户特批时必填**、客户等级时留空。**UI 要有「审批编号」列**（仅当存在客户特批行时出现，非特批行显示「—」）。原「一期恒为空、UI 无该列」作废 |
| 审批编号·★ 一期边界 | **一期是「人工录入编号」，不对接飞书审批流**——不做审批单同步、不做「审批中/已通过」状态机、不做回调、不做外键关联。审批编号**仅作追溯凭据**。⚠️ 审批流自动对接仍留二期 |
| **21. 泡比优惠进一期** | 泡比优惠由 Phase 2（模块 M，4 项）**整体改为 Phase 1**。原「泡比优惠一期不做 / 一期不建数据 / 一期不出现入口」作废。**Phase 1 功能数 55 → 59**，模块 M 优先级 **P2 → P0** |
| 泡比优惠·一期口径 | 泡比/密度阈值阶梯 + **固定减免** + 客户等级/客户特批 + 永久有效/固定期限 + 费用方向固定应收 + 审批编号（特批时）。匹配：泡比 = 实重(kg) ÷ 体积(m³)，≥ 阈值即命中；**多条命中取阈值最大那一档（不是叠加）**；**与运费优惠叠加** |
| **22. 优惠唯一性的精确口径（2026-09-12 落定）** | **同一父实体 × 同一对象类型 × 同一目标，最多一条「生效中」的规则**。三个要点：① **只看生效中**——`WHERE status=生效中`，已失效的历史规则**不占用名额**（否则"失效后想重新配一条"会被莫名拦住）；② **命名空间按对象类型分离**——客户特批比客户ID、客户等级比等级ID，同一 ID 值在两边**不算冲突**；③ **泡比优惠另加「密度阈值」维度**——键为 父实体 × **密度阈值** × 对象类型 × 目标，**同一目标在不同阈值档可各配一条**（这正是"阶梯"的语义，不可一刀切为一条）。**作用域 = 同一父实体（组合/附加费规则）内**，不做全系统唯一（理由：优惠天然挂在组合上，同一客户在不同组合享受不同减免是正常业务；若强制全系统唯一，则要么把"组合"塞进优惠目标、要么只能全渠道同一金额，会砍掉定价自由度） |
| **仍留 Phase 2（未动）** | ① **`单次有效`** 有效期类型；② 运费优惠 / 泡比优惠一期**仍只有固定减免**（附加费优惠一期两种都有）；③ 浮动优惠（券/满减/限时活动）；④ 营销模块独立立项；⑤ 叠加顺序可配；⑥ **飞书审批流自动对接** |

### ✅ E9 已定（2026-09-12 产品确认）——「看录入方式」而不是「算不算」

**结论**：查价阶段**能否**算出「超重超长」**取决于包裹信息的录入方式**：

| 包裹录入方式 | 查价阶段能否算 | 展示 |
|:---|:---|:---|
| **按单箱录入**（填了长/宽/高） | ✅ **能算** —— 超重超长按公式判定（该规则计价单位**仅按箱**）；**体积重 = 长 × 宽 × 高 ÷ 计泡系数** | **作预估展示** |
| **按总体重量与体积录入**（无单箱长宽高） | ❌ **算不出**（缺长宽高） | **不展示该项** |

- **规则口径不变**：「字段&公式」型规则的**正式触发与费用流水生成仍在「拣货」节点**；查价阶段只是**预估展示、不落库、不进账单**
- **正式计费以「拣货实测」为准**（客户自填尺寸仅供预估）→ 结果区提示条**保留**，继续声明"以拣货实测为准"
- **落点**：超级运价 RDD §8.7 注 + 数据设计 §6.1 链路图；货主端 RDD §5 R12a / 流程图说明 / §13、PRD §5.3 · R08a · §14、数据设计 §2.4 · §8（均已由"待确认"改为已定）

> 💡 这个答案原本就写在原型里：**超重超长的规则类型是「字段&公式」、计价单位按箱** —— 而单箱才有长宽高，总体重量体积没有尺寸，自然算不出。**是我一开始把它当成"算不算"的口径问题，方向错了。**

### ✅ `材积重` 口径已定（2026-09-12）

**结论**：**货箱上的「材重」与「重量方数」都属于材积重** —— 「材积重」是**体积重的统称**，按计费方式取其一：

| 计费方式 | 取货箱上的 | 算法 | 原型系数 |
|:---|:---|:---|:--:|
| 按 **KG** | **材重** | `长 × 宽 × 高 ÷ 计泡系数` | 6000 |
| 按 **m³** | **重量方数** | `实重 ÷ 计方系数` | 363 |

- 公式条件里直接引用 `材积重` 即可，不用自己写换算式
- **原型上不再解释取数来源**（小祖宗要求删除）：只保留变量名 `长、宽、高、重量、材积重`；**取数口径写在产品文档里**（超级运价 RDD §8.4 字段表 / PRD §5.10 / 数据设计 §3.14 的 `formula_list` 备注）
